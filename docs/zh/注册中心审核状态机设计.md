# 注册中心审核状态机设计

> 需求 30（issue #83）· 交付于 PR #84（v1.0.2）
> 单一实现参照：`agent_registry/status.py`（状态策略单点定义）

## 1. 概述

注册中心原有的注册审核模型是隐式两态（`registered` → `published`），发布者、审核者与消费者无法回答"我的注册走到哪一步、为什么被拒"。本设计将审核生命周期升级为**显式、可查询的状态机**：

- 四态：`registered`（待审核）、`published`（已发布）、`rejected`（已拒绝，终态，必填反馈）、`deprecated`（已弃用，终态）
- 每次审核驱动的转换记录 **原因 + 操作人 + 时间**，形成可审计轨迹
- 发布者可随时查询自己卡片的当前状态与转换历史
- 转换以 Outbox 事件对外广播，订阅者契约增量兼容

对标 AWS Agent Registry 的 curator 模型（PENDING_APPROVAL / APPROVED / REJECTED / DEPRECATED，每次转换必填 status reason）。

## 2. 状态定义

| 存储值 | API 规范名（写入别名） | 中文 | 语义 | 可被发现 |
|---|---|---|---|---|
| `registered` | `PENDING_REVIEW`（接受 `pending_review`） | 待审核 | 已存储、等待审核 | 否 |
| `published` | `APPROVED`（接受 `approved`） | 发布 | 审核通过 | **是** |
| `rejected` | — | 已拒绝 | 审核未通过，**必填原因**，终态 | 否 |
| `deprecated` | — | 已弃用 | 退役/被替代/已知问题，终态 | 否 |

兼容规则：

- 存储值保持小写遗留字符串，存量行与既有客户端不受影响
- 写路径大小写不敏感，`STATUS_ALIASES` 把规范名映射回存储值
- **遗留 NULL 状态按 `published` 处理**（与升级前所有读路径的历史行为一致），升级零迁移

## 3. 转换矩阵

```
registered ──approve──→  published        （CLI approve / 管理端发布）
registered ──reject───→  rejected         （原因必填）
registered ──deprecate→  deprecated       （原因必填）
published  ──unpublish→  registered       （下架，回待审核）
published  ──deprecate→  deprecated       （原因必填）
rejected   ──resubmit─→  registered       （owner 全量替换 PUT，原因记 resubmitted）
rejected   ──deprecate→  deprecated       （原因必填）
deprecated                （终态，无出边）
```

机器定义（`status.py` 的 `REVIEW_TRANSITIONS`，代码与文档以它为准）：

```python
REVIEW_TRANSITIONS = {
    'registered': frozenset({'published', 'rejected', 'deprecated'}),
    'published':  frozenset({'registered', 'deprecated'}),
    'rejected':   frozenset({'registered', 'deprecated'}),
    'deprecated': frozenset(),
}
```

- **非法转换**：`ValueError` → HTTP **409**（例如 `published → rejected` 非法——需先下架再拒绝）
- **同状态写**：幂等 no-op，始终允许
- **`deprecated` 不可逆**：恢复方式是作为一次新提交重新发布（遵循 AWS 模型）
- **重提交语义**：仅 `rejected` 卡可重提交——owner 通过既有全量替换 `PUT` 更新卡片，记录自动回到 `registered` 并保持不可见，历史记录原因 `resubmitted`；`deprecated` 卡无重提交路径

## 4. 可见性策略（单点定义）

`status.py:is_discoverable_status()` 是"可发现"的唯一判定，持久层、RegistryCore 与所有公开读写面共用：

- 仅 `published` 可被发现；`registered` / `rejected` / `deprecated` 一律不进入列表、语义检索与订阅流
- 空状态（升级前的存量记录）视为可发现，保持历史行为
- 待审卡不可能从某一条路径漏出而被另一条路径隐藏

## 5. 状态历史（审计轨迹）

每次转换追加一行：`from_status → to_status`、原因、操作人、时间戳。

**SQL 后端**（PostgreSQL / GaussDB / MySQL / SQLite 四方言，`sql_queries.py`）：

```sql
CREATE TABLE IF NOT EXISTS agent_status_history (
    id            SERIAL PRIMARY KEY,        -- 方言自增
    name          VARCHAR(100) NOT NULL,
    organization  VARCHAR(100) NOT NULL,
    from_status   VARCHAR(20),
    to_status     VARCHAR(20) NOT NULL,
    reason        VARCHAR(1000) NOT NULL DEFAULT '',
    operator      VARCHAR(100) NOT NULL DEFAULT '',
    created_at    VARCHAR(64) NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_status_history_key
    ON agent_status_history(name, organization);
```

- 纯增量表：`CREATE TABLE IF NOT EXISTS` 自动建表，**绝不 ALTER `agent_card`**，存量库零迁移
- **文件存储后端**：历史作为元数据 sidecar 存于 `agentregistry.json`，每卡上限 **50 条**（`MAX_STATUS_HISTORY`），超出截断最旧
- 删除卡片时级联清理其历史

## 6. REST API

审核操作沿用管理端口鉴权；`{org}` / `{name}` 为组织与卡名（URL 编码）。

### 6.1 拒绝

```
POST /rest/v1/registry-center/agent-cards/{org}/{name}/reject
Content-Type: application/json

{"remark": "能力描述与实测不符"}
```

- `remark`（原因）**必填**，缺失返回 400
- 当前状态不允许该转换返回 **409**（`Invalid status transition ...`）
- 卡不存在返回 **404**

### 6.2 弃用

```
POST /rest/v1/registry-center/agent-cards/{org}/{name}/deprecate
Content-Type: application/json

{"remark": "已被 v2 替代"}
```

语义同上；`published` 卡也可直接弃用（无需先下架）。

### 6.3 查询审核轨迹

```
GET /rest/v1/registry-center/agent-cards/{org}/{name}/review-status
```

响应（`history` 最新在前）：

```json
{
  "agent_name": "demo-review-c",
  "organization": "OpenAN-Demo",
  "status": "rejected",
  "last_transition": {
    "from_status": "registered",
    "to_status": "rejected",
    "reason": "UI demo: rejected state badge",
    "operator": "127.0.0.1",
    "at": "2026-10-15T14:41:07"
  },
  "history": [
    {
      "from_status": "registered",
      "to_status": "rejected",
      "reason": "UI demo: rejected state badge",
      "operator": "127.0.0.1",
      "at": "2026-10-15T14:41:07"
    }
  ]
}
```

发布者凭此回答"我的注册在哪一步、为什么"。

### 6.4 管理列表状态过滤

```
GET /rest/v1/registry-center/agent-cards/manage?status=rejected
```

响应含分态计数 `statusCounts`（`{"published": 5, "registered": 9, "rejected": 1, "deprecated": 2, ...}`），支撑审核队列视图。

## 7. 事件

新增 Outbox 事件类型（`broadcast/events.py`）：

| 事件 | 触发 |
|---|---|
| `AGENT_REVIEW_REJECTED` | `* → rejected` |
| `AGENT_REVIEW_DEPRECATED` | `* → deprecated` |

- payload 只含 **卡名、组织、原因** —— 不携带卡片内容（拒绝/弃用是治理动作，不是分发动作）
- 与既有 `AGENT_*` 事件共用 Outbox 投递保障；`registry_version` 游标对账契约不变
- 订阅者忽略未知事件类型即保持兼容（增量事件）

## 8. CLI 与 Web

**CLI**：

- `approve` 拒绝为 `deprecated` / `rejected` 的卡（非法转换直接报错）
- `approve` 的可选 remark 作为审核原因记入历史
- `unpublish` 对应 `published → registered`

**Web（registry-center 插件，CLI v1.0.2）**：

- 四态徽章，中英文各就各位：发布 / 待审核 / 已拒绝 / 已弃用（Published / Pending Review / Rejected / Deprecated）
- Agent 表格操作列「轨迹」按钮 → 弹窗调用 `review-status`，展示当前状态 + 时间线（状态、`from → to`、原因、操作人、时间），最新在前
- 审核动作（通过 / 拒绝 / 弃用）保留在注册表视图；轨迹弹窗为只读查询
- 不可用的发布按钮按状态自动隐藏

## 9. 兼容性声明

| 项 | 结论 |
|---|---|
| REST 契约 | 不变；reject / deprecate / review-status 为新增端点 |
| 存量数据 | 零迁移：唯一新表 `CREATE TABLE IF NOT EXISTS` 自动建；NULL 状态视为 published |
| 事件 | 新类型增量添加；游标对账机制不变 |
| 状态值 | 存储保持遗留小写字符串；规范名仅作为写入别名 |
| 部署 | 附带签名材料未配置时的 signer 降级告警修复（原升级 503 问题，见 PR #84 提交 799d6b0） |

## 10. 刻意延后项

- **DRAFT 状态**（发布者侧迭代态，可选需求）：注册入口已有签名验证把关，暂不引入
- **集成端口的 `?status=` 过滤**：消费端口保持仅 published 可见的保证不变
- **版本链 / 双版本 / 灰度**：独立需求（见 issue #83 No-Goals）
